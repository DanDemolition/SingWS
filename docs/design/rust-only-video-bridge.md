# Plan: retire the Objective-C video bridge (Rust only)

Written 2026-11-09 after the operator asked for "everything to work with Rust". NOT started. Nothing here changes a show until a step is built, rehearsed and installed.

## Where things stand (inspected, not assumed)
- The Rust bridge (`rust/crates/singws-video`, `libsingws_video.dylib`) is the DEFAULT (`video_bridge` = "rust", `0.2.18.1.py` ~4437, applied at ~22965) and has driven every Intel show since 2026-10-11. In the local logs the launch line is always `[VIDEO-BRIDGE] using the Rust video bridge`; no fallback line was found.
- The Objective-C bridge (`native/mpv_bridge/bridge.mm`, 1,956 lines, built into `libsingws_mpv_bridge.dylib`) survives as a safety net in `mpv_playback_iina.py`:
  1. `_open_bridge_library()` (~105): library missing / will not load / missing exports -> Objective-C.
  2. `_fallback_to_objc()` (~222, called ~342): the Rust bridge loaded but could not create a renderer for a song -> the WHOLE session switches to Objective-C.
  3. The environment default `SINGWS_VIDEO_BRIDGE` is "objc" when unset (tests and tools), and a saved `video_bridge: "objc"` selects it.
- Both build scripts compile/copy it (`build_singws_mac_arm64.sh` ~68 builds it, `build_singws_mac_intel.sh` ~70 takes the tracked copy), both specs REQUIRE it (`SingWS-*.spec` ~146-154: the build aborts without it), and two tracked dylibs under `native/mpv_runtime/artifacts/*/Frameworks/` are regenerated by every build (that is why they show as modified).
- Things that look related but are NOT the bridge: `rust/crates/singws-shell/src/selfcheck.rs` uses `objc_msgSend` only for read-only AppKit questions; the mpv runtime (`singws_libmpv.2.dylib`) stays (the Rust bridge dlopens it).
- Files that mention it (git grep): `mpv_playback_iina.py` (16), `test_video_bridge_selection.py` (12), `0.2.18.1.py` (8), `test_bg_video_lyrics.py` (7), the two build scripts, the two specs, `native/mpv_bridge/*`, `tools/video_bridge_*.py`, `test_rust_video_bridge.py`, `test_performance_safety.py`, and about 15 more tests/tools with one mention each.

## The one real risk
With the fallback gone, "the Rust bridge cannot create a renderer for this song" becomes a visible failure instead of a silent switch. So the work is mostly about what happens THEN, not about deleting code.

## Steps (each is its own small change; stop after each)
1. **Make the failure visible and the opt-out dead, delete nothing.** Default the environment to Rust; migrate a saved `video_bridge: "objc"` to "rust" at launch (like the other launch migrations, logged); when Rust fails, KEEP the fallback but log an ERROR line and show the operator a notification ("video engine fallback used"). Ship it, run one or two shows, and read the logs. If any show hits the fallback, stop and fix the Rust cause first.
2. **Rust-only behaviour (flag first).** New setting `video_bridge_fallback` (default True = today). With it False: a renderer failure retries creating the core once, then the song continues with its sound but no picture and a clear on-screen error, never a silent switch. Add a forced-failure test (bad libmpv path) and LOOK at it on screen (AGENTS rule 4).
3. **Stop building and bundling the Objective-C bridge.** Remove the compile/copy from both build scripts and the "required" check from both specs; build both installers; scratch-launch (arm64 native, Intel under Rosetta) and rehearse on the real Intel Mac (CDG, MP4, background video, rotation screen, window resize/hide) before any show.
4. **Delete the code.** `git rm` `native/mpv_bridge/`, the two tracked dylibs (and the `-intel` copy), `_fallback_to_objc`, the `objc` branches in `mpv_playback_iina.py`, the `video_bridge` setting, the dead tests and tools; update `HANDOFF.md`/docs. Git history is the rollback for the source; the installed backups are the rollback for the app.

## Rollback at every step
Keep the previous app (`/Applications/SingWS-...-pre-*.app`) and the previous Intel DMG. Steps 1-2 are one-line reverts (the flag/setting); step 3 needs the previous installer; step 4 only happens after steps 1-3 have run clean.

## Not decided (needs the operator)
- What a live show should do on a renderer failure: retry once then continue audio-only (proposed), or stop the song and return it to the queue.
- Whether to keep the Windows port in mind (a Rust bridge is the part that makes it possible; the Objective-C one never could).

## Verification per step
Unit tests with a scratch `SINGWS_HOME`, a scratch-profile launch of the built app, an on-screen look (screenshot) at CDG + MP4 + background video, and for steps 3-4 a rehearsal on the real Intel Mac. A passing test suite alone proves nothing here: renderers cannot be validated by tests.
